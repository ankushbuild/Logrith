The reason so many sizes exist isn't redundancy — each platform requests its expected size directly rather than scaling down a single large image itself, which means providing the exact requested size produces a sharp result, while providing only one size forces every other context to either scale (introducing blur) or fall back to a generic default icon.

Why Favicons Grew from One Size to Six or More

The original favicon.ico format dates back to the mid-1990s, when it needed to serve exactly one purpose: a small icon shown next to a browser bookmark or in the address bar. As the web evolved to include mobile browsing, home-screen app-like experiences, and eventually full Progressive Web Apps that behave like installed native applications, each new context brought its own icon requirement, layered on top of rather than replacing the original. iOS introduced its own touch icon convention when Safari added the ability to save a web page to the home screen looking like a native app icon. Android and the broader web platform later introduced the web app manifest, requiring specific icon sizes for home screen and splash screen display. The result is that a genuinely complete, modern favicon setup accumulated requirements across roughly three decades of web platform evolution, rather than being designed as one coherent system from the start.

Adding the Correct HTML Tags

Generating the image files is only half the task — browsers and devices need to be told where to find each size via link tags in your HTML head section. A typical complete set looks like:

<link rel="icon" href="/favicon.ico">
<link rel="icon" type="image/png" sizes="32x32" href="/favicon-32x32.png">
<link rel="icon" type="image/png" sizes="16x16" href="/favicon-16x16.png">
<link rel="apple-touch-icon" href="/apple-touch-icon.png">
<link rel="manifest" href="/site.webmanifest">

The 192x192 and 512x512 sizes are typically referenced not directly in the HTML head, but within a site.webmanifest JSON file, which the manifest link tag above points to — this file also defines other PWA-related metadata like the site's name and theme color, with the icon sizes listed as part of that structure.

Understanding site.webmanifest

The web app manifest file — typically named site.webmanifest — is a JSON file that describes how your site should behave when saved to a home screen or installed as a Progressive Web App. Beyond just listing icon sizes, it typically defines the site's display name, background color, theme color, and display mode (whether it opens in a full browser window or a standalone app-like window). A minimal manifest referencing your generated icons looks roughly like a JSON object with a "name" field, a "short_name" field for space-constrained display, and an "icons" array listing each icon's source path, size, and MIME type. Getting this file right matters specifically for the Android and PWA-related icon sizes — without a correctly structured manifest referencing them, those larger icon sizes won't be picked up even if the image files themselves exist and are correctly generated.

Choosing the Right Source Image

Since every generated size is scaled down from your uploaded source image, starting with a genuinely high-resolution, square source produces the best results across the board — a source image smaller than the largest generated size (512x512) means that largest size will itself be upscaled, introducing softness exactly where maximum clarity matters most for larger display contexts. A simple, bold design tends to translate better across sizes than intricate detail, since a favicon is frequently viewed at genuinely tiny sizes where fine detail simply isn't visible regardless of source quality.

Real-World Scenarios

  • "My site launched but the browser tab just shows a generic icon." Confirm your favicon.ico or 32x32 PNG is correctly referenced and actually accessible at the path specified in your HTML.
  • "I saved my site to my iPhone home screen and it shows a screenshot instead of my logo." This means the apple-touch-icon link tag is missing or pointing to an incorrect file — iOS specifically looks for this tag rather than falling back to a generic favicon size.
  • "My PWA installs but shows a blank or broken icon." Check your site.webmanifest file references the 192x192 and 512x512 icons correctly, since PWA installation relies specifically on the manifest rather than the HTML head tags alone.
  • "I'm rebranding and need to update my favicon everywhere." Regenerate the full size set from your new logo and replace all existing favicon files at their same paths — browsers can aggressively cache favicons, so a hard refresh may be needed to see the update.

Why Favicon Updates Sometimes Don't Show Immediately

Favicons are among the most aggressively cached assets on the web, since browsers reasonably assume an icon representing a site's identity won't change often, and re-fetching it on every visit would be wasteful. This means that after updating your favicon files, visitors — and sometimes even you, testing your own changes — may continue seeing the old icon for some time, even after the new files are correctly deployed. A hard refresh, clearing browser cache specifically for your site, or in some cases simply waiting for the browser's own cache expiration can be necessary to see an update reflected. This isn't a sign that something went wrong with the generation or deployment — it's expected caching behavior worth knowing about ahead of time.

Common Mistakes

  • Starting from a low-resolution source image. Upscaling a small source to fill the 512x512 size produces a soft result — start from at least 512x512 for best results across all sizes.
  • Forgetting to add the HTML link tags. Generated image files alone do nothing without the corresponding link tags referencing them in your site's head section.
  • Using an overly detailed design. Fine detail disappears at 16x16 pixels — favor simple, bold shapes that remain recognizable at genuinely tiny sizes.
  • Not testing across actual devices. Browser tab icons, iOS home screen icons, and Android icons each render slightly differently — checking your favicon in an actual browser tab and an actual mobile home screen confirms everything displays correctly.

Favicon Best Practices for Different Site Types

The general guidance above applies broadly, but a few site categories have slightly different practical priorities worth calling out specifically. E-commerce and business sites benefit most from getting the browser tab icon (16x16/32x32) and Apple touch icon exactly right, since these are the icons customers see most frequently across repeat visits and bookmarks — a recognizable, on-brand icon here reinforces trust more than the PWA-specific sizes do for a typical shopping site. Web apps and tools genuinely intended to be installed as PWAs should prioritize getting the 192x192 and 512x512 sizes correct within a properly structured manifest, since a broken or missing icon at install time creates a noticeably worse first impression than a slightly imperfect browser tab icon would. Blogs and content sites sit somewhere in between — the browser tab icon matters most for everyday browsing, while the other sizes provide a complete, professional setup without necessarily being the primary concern.

Testing Your Favicon Setup Thoroughly

Once generated files are deployed and HTML tags added, a few quick checks confirm everything is actually working rather than assuming it is. Open your site in a private/incognito browser window (which bypasses most caching) and check the browser tab directly. On a mobile device, try adding the site to your home screen and confirm the icon that appears matches your design rather than a generic placeholder or screenshot. If your site has a PWA manifest, browser developer tools typically include an "Application" or "Manifest" panel that reports whether the manifest loaded correctly and which icons it found — a genuinely useful way to catch a misconfigured manifest path before a real user encounters the broken result on their own device.

Frequently Asked Questions

What favicon sizes does a modern website actually need?

At minimum, 16x16 and 32x32 for browser tabs, 180x180 for Apple touch icon, and 192x192 plus 512x512 for Android and PWA icons. A favicon.ico covering multiple sizes is also still widely supported.

Why do I need so many sizes instead of just one?

Different platforms request their specific size directly rather than scaling one image themselves — providing the exact size avoids blurry scaling in each display context.

What image should I start with?

A square image at least 512x512 pixels works best, since every generated size is scaled down from this source.

Do I need to add HTML tags manually?

Yes, generating the files is only half the setup — you also need the correct HTML link tags in your site's head section for browsers and devices to find them.

Why doesn't my updated favicon show up immediately?

Favicons are aggressively cached by browsers. A hard refresh, clearing cache for your site, or waiting for cache expiration is often needed to see an update reflected.

Is a favicon.ico file still necessary alongside PNG versions?

It's still checked by default by some browsers and tools that look for it at the root path regardless of other link tags present, so including it alongside PNG versions remains good practice for maximum compatibility.

Conclusion

A complete, correctly-sized favicon set is a small detail that shows up in nearly every context a visitor encounters your site — the browser tab, a saved bookmark, a home screen icon. Generating every size from one good source image, then wiring up the correct HTML references and manifest, is a short setup task that avoids the blurry or missing icons that come from providing just one size and hoping every platform scales it acceptably. Understanding the caching behavior and how each size maps to a specific platform context makes the whole system feel far less mysterious than it initially appears.
